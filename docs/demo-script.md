## 一句話

上班族在松山車站按一下，平台替他配一台剛好要開進內科、還有空位的私家車；駕駛開車時只需要按「確認」。

## 角色與畫面

| 角色 | 帳號 | 在哪裡操作 | 給誰看 |
|---|---|---|---|
| 台上的駕駛 | `driver4` | 展示頁左邊的手機 | 觀眾 |
| 乘客 | `passenger1` | 展示頁右邊的手機 | 觀眾 |
| 另一位真人駕駛 | `driver5` | 台下另一個分頁（或另一支手機）`http://localhost:5173/?account=driver5` | 不給觀眾看，只用來「婉拒」 |
| 模擬車 | `driver1`～`driver3` | 台下的模擬器分頁 `http://localhost:5173/?debug=1` | 不給觀眾看 |

- 展示頁：`http://localhost:5170`。兩支手機都是 390px 寬，右上角有「重設」。
- `driver4`、`driver5` 都在「我的標籤」帶「可帶寵物」；模擬車都沒有。乘客把「可帶寵物」設成「強制」，請求就只會配給台上的兩位真人駕駛。
- `driver4` 帶入上次的設定：松山車站 → 瑞光路 513 巷、可載 3 人、不自動接受。`passenger1` 帶入常用目的地瑞光路 513 巷，以及可接受的公車站「瑞光港墘路口」「港墘路」。

## 事前準備

當天早上做一次，換機器時重做。

1. 根目錄 `.env` 要有：
   - `MAP_API_KEY`：後端用 Google Routes 算真實路線。
   - `VITE_GOOGLE_MAPS_API_KEY`：瀏覽器顯示地圖、搜尋地點。這把金鑰要開啟 Places API (New)。
2. 啟動全部元件：
   ```sh
   just demo
   ```
   這會依序啟動 PostgreSQL、套用遷移、以 `DEMO_RESET=1` 啟動後端，再啟動兩個介面與展示頁。後端的 log（`backend/.run/server.log`）要看到下面兩行：
   - `travel estimates: google (MAP_API_KEY is set)`
   - `DEMO_RESET is on`

   沒有 just 時，照 `justfile` 裡 `demo` 的步驟逐一執行。
3. 開好分頁：
   - 分頁 1：展示頁 `http://localhost:5170`，投影出去的就是這一頁。
   - 分頁 2：模擬器 `http://localhost:5173/?debug=1`。
   - 分頁 3：`driver5` 的手機畫面 `http://localhost:5173/?account=driver5`。
4. 用新的瀏覽器設定檔或無痕視窗開展示頁。乘客的篩選條件會記在瀏覽器裡（7.1），Demo 的重設清不掉。

## 開演前 3 分鐘

這段不給觀眾看，或當作開場白的背景。

1. **重設**：在展示頁按「重設」兩次。兩支手機會重新載入，回到起點。
2. **開始模擬**：到分頁 2，按左邊的「除錯」→「開始模擬」。重設後一定要重新整理這一頁、再按一次，模擬器才會從頭開始。
3. **`driver5` 出發**（台下，用指令最快）：
   ```sh
   curl -X PUT  http://localhost:8080/api/me/tags/5 -H 'Authorization: Bearer driver:driver5'
   curl -X POST http://localhost:8080/api/driver/trips -H 'Authorization: Bearer driver:driver5' \
     -H 'Content-Type: application/json' \
     -d '{"pickup_point_id":1,"destination":{"name":"瑞光路 513 巷","lat":25.0765,"lng":121.5742},"capacity":3,"auto_accept":false,"tag_filters":[]}'
   ```
   第一行選「可帶寵物」，第二行出發。5 是種子資料裡「可帶寵物」的編號；資料庫換過或種子改過時，先用下面的指令確認編號，再把第一行的 5 換掉。選錯標籤，請求就不會配給台上的駕駛：
   ```sh
   curl -s http://localhost:8080/api/tags -H 'Authorization: Bearer driver:driver5'
   ```

   分頁 3 重新整理後，應該看到「行程中／目前沒有搭車請求」。
4. **`driver4` 出發**：等 `driver5` 出發約 30 秒，在展示頁左邊的手機上：
   - 看一眼「今天載人嗎？」：地圖畫出松山車站 → 堤頂大道一段 → 瑞光路 513 巷的真實路線，**沒有**「路線為估算」。
   - 打開「我的標籤」，確認「可帶寵物」已選取（選一次後會保留，重設不會清掉）。
   - 按「我出發了」，畫面換成深色的「行程中／目前沒有搭車請求」。
5. **等待提示**：看分頁 2 的模擬器，`driver4` 顯示「移動中 12%」左右時（約 1 分 40 秒後），就可以開始計時。這時 `driver4` 大約在上車點前 500 公尺，`driver5` 約 15%，比 `driver4` 更靠近上車點。

> 開場想讓觀眾看到「駕駛出發、地圖顯示行程路線」，就把第 4 步放在台上做，再接一段約 1 分 40 秒的開場白。台上的 2 分鐘從下面的 0:00 開始算。

## 台上 2 分鐘

時間是實測值：兩次預演都是 97 秒走完。下表的時間另外留了講話的時間。

| 時間 | 操作 | 畫面上看到 | 講者說 |
|---|---|---|---|
| 0:00 | 指著右邊的乘客 | 「松山車站／距離 20 公尺／最快 3 分鐘到」，時間軸上幾台車正在接近 | 「上班族到了松山車站，打開 App 就知道接下來幾分鐘有幾台車要開進內科、還有幾個空位。不用選車，平台會替他配。」 |
| 0:15 | 乘客按「今天我要搭」；在篩選中把「可帶寵物」設成「強制」、「不抽菸」設成「建議」；按「送出請求」 | 「正在等駕駛確認」 | 「他帶著寵物，這是硬條件；不抽菸只是偏好。」 |
| 0:25 | 分頁 3（`driver5`，台下）按「婉拒」 | 乘客：「上一位駕駛無法載你，已改配下一台車。」左邊的駕駛畫面整片變黃：「有乘客要搭車／上車 松山車站／下車 瑞光路 513 巷」 | 「第一位駕駛今天不方便，平台立刻改配下一台。駕駛開車時不用看地圖，只看到上哪、下哪，一個大按鈕。」 |
| 0:35 | 駕駛按「確認」 | 乘客：「幾分鐘後到」、車牌 DEF-4567、藍色 Mazda 3，地圖上的車沿路開過來；下方小字「這台車不完全符合你的建議標籤」 | 「確認了。這台車沒有『不抽菸』，平台仍然配給它並清楚標示『已放寬』：建議條件只加分，不會讓乘客多等。地圖上的車頭跟著實際行進方向轉。」 |
| 約 1:30 | 等車開到 | 乘客：「車已到上車點」 | 「車到了。」 |
| 1:35 | 乘客按「我已上車」 | 乘客：「在瑞光路 513 巷下車」；駕駛：乘客那一列變成「在車上」 | 「上車之後，乘客只剩一個按鈕。」 |
| 1:45 | 乘客按「我已下車，結束共乘」 | 乘客：「共乘完成／路上少了一台車。」；駕駛的乘客列消失 | 「一趟共乘結束，路上少了一台車。」 |

注意：

- 已確認畫面的「幾分鐘後到」來自 Google 的即時路況（例如「4 分鐘後到」），但模擬車固定以時速 25 公里前進，實際約 1 分半就到。講者不要照著數字說「還要 4 分鐘」。
- 送出後約 1～2 秒（下一次輪詢）`driver5` 的畫面才變黃；看到黃色再按「婉拒」。

## 收尾

`driver4` 繼續沿路線開往瑞光路 513 巷，約 10 分鐘後抵達目的地（從乘客上車算起），行程自動結束（T21），左邊的手機換成「行程結束／已到達目的地／瑞光路 513 巷／這趟載了 1 位乘客」，按「好」回到「今天載人嗎？」。

2 分鐘內等不到這個畫面：可以在問答之後再切回展示頁給大家看，或事先截圖放在簡報最後一頁。

## 再演一次

1. 展示頁按「重設」兩次。
2. 從〈[開演前 3 分鐘](#開演前-3-分鐘)〉的第 2 步做起：重新整理模擬器分頁、按開始；再讓 `driver5`、`driver4` 依序出發。
3. 乘客的篩選會保留上一次的「可帶寵物 強制、不抽菸 建議」，送出前看一眼即可。

兩次預演中，重設後再演一次都順利走完，第二次同樣是 97 秒。

## 出狀況時

| 狀況 | 現場看到 | 怎麼辦 |
|---|---|---|
| **斷網**（後端連不到 Google） | 路線預覽改用估算，並標「路線為估算」；看板、已確認畫面的時間標「估算」 | 照常演，流程完全一樣，只是時間變成估算值。可以順口說「斷網時平台改用估算，並清楚標示」 |
| **斷網**（瀏覽器也斷了） | 地圖底圖不出來；目的地無法搜尋 | 照常演：劇本只用預先帶入的目的地，不需要搜尋；地圖空白不影響操作 |
| **重設失敗** | 展示頁出現紅字「重設失敗，請確認後端有在執行。」 | 確認後端在跑（`curl http://localhost:8080/api/ping`），再按一次重設；或在終端機執行 `just demo-reset`。還是不行，就 `just backend down` 後重新 `just demo` |
| **重設後乘客顯示「連線不穩」** | 另外開著、停在請求畫面的乘客分頁一直顯示「連線不穩」 | 重新整理那個分頁。展示頁的重設會自動重新載入兩支手機，不受影響 |
| **`driver4` 一直沒變黃** | 乘客一直停在「正在等駕駛確認」 | 看分頁 3 是否變黃：先變黃的是 `driver5`，按婉拒後才會輪到 `driver4`。若送出得太晚，`driver5` 已經經過上車點，請求會直接配給 `driver4`，跳過婉拒那段，照常往下演 |
| **乘客「目前沒有可搭的車」** | 送出後立即顯示 | 通常是兩位真人駕駛都已經經過上車點，或忘了讓 `driver5`、`driver4` 出發。按「回去看接近的車」，重設後從頭來 |
| **車一直沒到上車點** | 已確認畫面停住 | 模擬器分頁被關掉或停止了。到分頁 2 確認「移動中 %」有在增加，沒有就按開始 |

## 為什麼這樣安排

- **台上的駕駛用強制標籤收請求**：Go 依感受成本排序（REQ-042，design.md 4.11 媒合引擎），最近的模擬車（自動接受）通常最先拿到請求。只有台上的兩位真人駕駛帶「可帶寵物」，乘客設成強制後，請求就一定配給他們（ui-design 8.8）。
- **婉拒交給 `driver5`**：只有一位駕駛帶「可帶寵物」時，婉拒後沒有下一台符合的車，會變成「無車可配」。讓 `driver5` 早 30 秒出發、比 `driver4` 更接近上車點，請求會先配給 `driver5`；它婉拒後，改配給台上的 `driver4`，後面的上車、結束共乘、行程結束都在台上那支手機發生。
- **標籤效果演「已放寬」**：同一個請求裡把「不抽菸」設成建議。符合強制條件的兩台車都沒有不抽菸，平台照樣配給最快的車，並標示「已放寬」，正好說明「建議只加分、不讓乘客多等」的取捨（REQ-047）。不另外安排「標籤勝出」，因為那需要讓幾台車的等待時間接近，現場不好控制。
- **只用一位乘客**：一位乘客有未結束的請求時不能再送出（REQ-069）。取捨、婉拒、確認都在同一個請求裡，就不需要換乘客，也不用先結束共乘再送第二次。
- **`driver5` 用指令出發**：`driver5` 沒有上一趟行程（用來展示第一次使用），在介面上出發要搜尋目的地，現場多一步也多一個風險。用指令出發，目的地和 `driver4` 相同，模擬器的路徑也開得到。
