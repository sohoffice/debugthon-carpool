## 一句話

上班族在松山車站按一下，平台替他配一台剛好要開進內科、還有空位的私家車；駕駛開車時只需要按「確認」。

## 角色與畫面

| 角色 | 帳號 | 在哪裡操作 | 給誰看 |
|---|---|---|---|
| 台上的駕駛 | `driver4` | 展示頁左邊的手機 | 觀眾 |
| 乘客 | `passenger1` | 展示頁右邊的手機 | 觀眾 |
| 另一位真人駕駛 | `driver5` | 展示頁自動操作（DD-45） | 不給觀眾看：`driver4` 出發時跟著出發，收到請求就自動「婉拒」 |
| 模擬車 | `driver1`～`driver3` | 展示頁的模擬器（DD-14） | 不給觀眾看 |

講者只開展示頁、只操作上面的兩支手機，不需要終端機。台下的事由展示頁自己做，順序是自動的，不需要等提示。

- 展示頁：`http://localhost:5170`。兩支手機都是 390px 寬，右上角是「開始 Demo」（開始後變成「重新開始」）。
- 右下角是給講者用的「手機｜市府戰情室」切換與收起來的「紀錄」（UD-30）。紀錄寫著台下發生的每一步（例如「driver5 婉拒了乘客 小美的請求」）；有錯誤時「紀錄」旁亮一個紅點，不會自己打開。
- `driver4`、`driver5` 的「關於我和車」都選了「我不抽菸」和「車上能放大件行李」；模擬車沒有一台兩個都有（`driver2` 只有能放行李，`driver3` 不抽菸但不能放行李）。乘客把「不抽菸」和「能放大件行李」都設成「一定要」，請求就只會配給台上的兩位真人駕駛。
- `driver4` 帶入上次的設定：松山車站 → 瑞光路 513 巷、可載 3 人、不自動接受。`passenger1` 帶入常用目的地瑞光路 513 巷，以及可接受的公車站「瑞光港墘路口」「港墘路」。

## 事前準備

當天早上做一次，換機器時重做。

1. 根目錄 `.env` 要有：
   - `MAP_API_KEY`：後端用 Google Routes 算真實路線。
   - `VITE_GOOGLE_MAPS_API_KEY`：瀏覽器顯示地圖、搜尋地點。這把金鑰要開啟 Places API (New)。
2. 啟動全部元件：
   ```sh
   just demo
   ```
   這會依序啟動 PostgreSQL、套用遷移、以 `DEMO_RESET=1` 啟動後端，再啟動兩個介面與展示頁。後端的 log（`backend/.run/server.log`）要看到下面兩行：
   - `travel estimates: google (MAP_API_KEY is set)`
   - `DEMO_RESET is on`

   沒有 just 時，照 `justfile` 裡 `demo` 的步驟逐一執行。
3. 清掉今天 Karate 留下的請求：Karate 和 Demo 共用 `carpool` 資料庫，Karate 送出的請求在情境結束時不會刪除，會和送出過請求的 `karate-` 帳號一起留在資料庫（見 [DEV.md〈API 整合測試（Karate）〉](../DEV.md#api-整合測試karate)）。今天留下的請求會被市府戰情室算成今天的真實請求，媒合率看起來很低。Demo 的重設不會清這些資料。Demo 當天不要跑 Karate，開演前在根目錄執行一次：
   ```sh
   lsof -iTCP:18080 -sTCP:LISTEN   # no output means no Karate backend is running
   docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -U carpool -d carpool <<'SQL'
   BEGIN;
   CREATE TEMP TABLE karate_requests ON COMMIT DROP AS
     SELECT q.id FROM ride_requests q JOIN users u ON u.id = q.passenger_id
      WHERE u.username LIKE 'karate-%'
        AND (q.created_at AT TIME ZONE 'Asia/Taipei')::date = (now() AT TIME ZONE 'Asia/Taipei')::date;
   -- The ledger and service record foreign keys block deleting the requests first.
   DELETE FROM driver_point_ledger
    WHERE service_record_id IN (SELECT id FROM service_records WHERE request_id IN (SELECT id FROM karate_requests));
   DELETE FROM service_records WHERE request_id IN (SELECT id FROM karate_requests);
   DELETE FROM ride_requests WHERE id IN (SELECT id FROM karate_requests);
   COMMIT;
   SQL
   ```
   `lsof` 有輸出代表 Karate 還在跑，等它結束再清。每一行 `DELETE` 後面的數字是刪掉的筆數，都是 0 代表今天沒有 Karate 的請求。要確認清乾淨了，就再執行一次同一段 SQL，三行 `DELETE` 都應該是 0。戰情室「今天」的數字含每天重新產生的模擬資料，每天都不一樣，不要拿來和固定的數字比對。
4. 開好分頁：只要一個，展示頁 `http://localhost:5170`，投影出去的就是這一頁。不要開第二個展示頁：兩個展示頁都按「開始 Demo」，會有兩個模擬器回報同一批車。
5. 用新的瀏覽器設定檔或無痕視窗開展示頁。乘客的篩選條件會記在瀏覽器裡（7.1），Demo 的重設清不掉。

## 開演前 3 分鐘

這段不給觀眾看，或當作開場白的背景。

1. **開始 Demo**：在展示頁按一次「開始 Demo」。按鈕顯示「執行中…」，幾秒後變成「重新開始」，兩支手機重新載入、回到起點。展示頁依序做了：
   - 重設 Demo（DD-29）。
   - 替 `driver4`、`driver5` 都選「我不抽菸」和「車上能放大件行李」（已選過就不變）。請求以強制標籤篩選駕駛（REQ-040），兩個標籤缺一個的駕駛都不會被配到；`driver4` 少了任何一個，`driver5` 婉拒後就沒有下一台車可配。
   - 開始模擬器，模擬車開始移動。之後展示頁一直替 `driver5` 操作：`driver4` 出發時跟著出發，收到請求就婉拒。

   按鈕下方出現紅字「開始失敗，請確認後端有在執行。」就見〈[出狀況時](#出狀況時)〉。
2. **`driver4` 出發**：在展示頁左邊的手機上：
   - 看一眼「今天載人嗎？」：地圖畫出松山車站 → 堤頂大道一段 → 瑞光路 513 巷的真實路線，**沒有**「路線為估算」。
   - 看一眼「關於我和車」顯示「我不抽菸、車上能放大件行李」（展示頁已替 `driver4` 選好，重設不會清掉）。
   - 按「我出發了」，地圖和設定消失，畫面換成「行程中／目前沒有搭車請求」。

   `driver5` 在 1～2 秒內往同一個目的地出發（觀眾看不到），模擬器也在 1～2 秒內開始回報 `driver4` 的位置，所以按下「我出發了」後就能接著演，不用等提示。`driver5` 的模擬路徑從上車點前約 400 公尺出發，比 `driver4` 的約 535 公尺近，同時出發時一定先到上車點、先收到請求。
3. **開場白**：接著講開場白，然後從下面的 0:00 開始。乘客要在 `driver4` 出發後約 1 分鐘內送出請求（0:15），之後 `driver5` 就經過上車點了，見〈[出狀況時](#出狀況時)〉的〈送出得太晚〉。

> 開場想讓觀眾看到「駕駛出發、地圖顯示行程路線」，就把第 2 步放在台上做，再接一段開場白。台上的 2 分鐘從下面的 0:00 開始算。

## 台上 2 分鐘

時間是預演的實測值，下表另外留了講話的時間。路徑縮短後（T33）只重新量了車程：`driver4` 出發後約 94 秒開過上車點；展示頁接手台下操作後（T62），整段劇本還沒有重新預演。

| 時間 | 操作 | 畫面上看到 | 講者說 |
|---|---|---|---|
| 0:00 | 指著右邊的乘客 | 「松山車站／距離 20 公尺／最快 3 分鐘到」，時間軸上幾台車正在接近 | 「上班族到了松山車站，打開 App 就知道接下來幾分鐘有幾台車要開進內科、還有幾個空位。不用選車，平台會替他配。」 |
| 0:15 | 乘客按「今天我要搭」；在「這趟車要」把「不抽菸」和「能放大件行李」設成「一定要」、「安靜坐車」設成「最好」；按「送出請求」 | 「正在等駕駛確認」 | 「乘客今天帶了一個大行李箱，又不想聞菸味，這兩個是硬條件；安靜只是偏好。」 |
| 0:25 | 不用操作：展示頁替 `driver5` 自動婉拒，紀錄寫「driver5 婉拒了乘客 小美的請求」 | 乘客的看板先顯示約 3 秒的「駕駛無法載你／正在改配下一台車…」，再回到「正在等駕駛確認」並多一行「上一位駕駛無法載你，已改配下一台車。」；約 2 秒後左邊的駕駛畫面才整片變黃：「有乘客要搭車／上車 松山車站／下車 瑞光路 513 巷」 | 「第一位駕駛今天不方便，平台立刻改配下一台。駕駛開車時不用看地圖，只看到上哪、下哪，一個大按鈕。」 |
| 0:35 | 駕駛按「確認」 | 乘客：「幾分鐘後到」、車牌 ABC-0004、藍色 Mazda 3，地圖上的車沿路開過來；下方小字「這台車沒有全部符合你選『最好』的條件」 | 「確認了。這位駕駛沒有標『開車喜歡安靜』，平台仍然配給它並清楚標示『已放寬』：『最好』只加分，不會讓乘客多等。地圖上的車頭跟著實際行進方向轉。」 |
| 約 1:30 | 等車開到 | 乘客：「車已到上車點」 | 「車到了。」 |
| 1:35 | 乘客按「我已上車」 | 乘客：「在瑞光路 513 巷下車」；駕駛：乘客那一列變成「在車上」 | 「上車之後，乘客只剩一個按鈕。」 |
| 1:45 | 乘客按「我已下車，結束共乘」 | 乘客：「共乘完成」，下方是「上車 松山車站 → 下車 瑞光路 513 巷」、「車上 N 分鐘」與車牌 ABC-0004；駕駛的乘客列消失 | 「一趟共乘結束，路上少了一台車。」 |
| 1:50 | 不用操作 | 乘客：「共乘完成」 | 「公車站與過去的車流是開放資料、路線用 Google，標『模擬』的都是模擬，詳見 README。」 |

注意：

- **真實與模擬資料的說明一定要講**：活動規則要求 Demo 時口頭說明。1:50 的一句約 5 秒，台上仍在 2 分鐘內。時間有餘就改說完整版：「資料說明：公車站是臺北市開放資料，路線和時間用 Google。過去上班日的車流是交通部運輸資料流通服務平臺（TDX）的實測，今天和 10/23 的車流是模擬，天氣也是模擬。帳號、車牌、車輛位置是模擬，畫面上紫色虛線框的『模擬』『估算』都不是實測。詳見 README。」分類以 [README〈真實資料與模擬資料〉](../README.md#真實資料與模擬資料) 為準。
- **標籤是使用者自己勾的，沒有經過驗證**。被問到「怎麼確定」時，就說 PoC 的標籤都是自己勾選；之後會加上企業認證的標籤（REQ-009～REQ-012，Phase 2），由公司幫員工背書。
- **被問到「能不能只配女性駕駛」**：平台刻意不記錄任何人的性別。讓使用者自稱「我是女性」，有心人就能用來鎖定特定對象；安心共乘改由企業認證的標籤處理（Phase 2）。
- **駕駛和乘客看到的是同一個標籤的兩種說法**：駕駛勾「車上能放大件行李」，乘客要求「能放大件行李」，配對時是同一個標籤（REQ-086）。
- 已確認畫面的「幾分鐘後到」來自 Google 的即時路況（例如「4 分鐘後到」），但模擬車固定以時速 25 公里前進，實際約 1 分半就到。講者不要照著數字說「還要 4 分鐘」。
- 送出後約 1 秒，`driver5` 被展示頁婉拒，乘客的看板顯示「駕駛無法載你」；再過約 2 秒（改配延遲），左邊的駕駛畫面才變黃。

## 收尾

`driver4` 繼續沿路線開往瑞光路 513 巷，約 10 分鐘後抵達目的地（從乘客上車算起），行程自動結束（T21），左邊的手機換成「行程結束／已到達目的地／瑞光路 513 巷／這趟載了 1 位乘客」，按「好」回到「今天載人嗎？」。

2 分鐘內等不到這個畫面：可以在問答之後再切回展示頁給大家看，或事先截圖放在簡報最後一頁。

## 再演一次

1. 在展示頁按「重新開始」，再按一次「再按一次確定重新開始」（3 秒內）。兩支手機重新載入，回到起點；模擬器不停，模擬車換了新的行程，從路徑起點重新開始。
2. 從〈[開演前 3 分鐘](#開演前-3-分鐘)〉的第 2 步做起。`driver5` 會在 `driver4` 出發時再跟著出發。
3. 乘客的篩選會保留上一次的「不抽菸、能放大件行李 一定要，安靜坐車 最好」，送出前看一眼即可。

不要重新整理展示頁：重新整理會停掉模擬器，按鈕回到「開始 Demo」，要再按一次（會重設）。

## 出狀況時

| 狀況 | 現場看到 | 怎麼辦 |
|---|---|---|
| **斷網**（後端連不到 Google） | 路線預覽改用估算，並標「路線為估算」；看板、已確認畫面的時間標「估算」 | 照常演，流程完全一樣，只是時間變成估算值。可以順口說「斷網時平台改用估算，並清楚標示」 |
| **斷網**（瀏覽器也斷了） | 地圖底圖不出來；目的地無法搜尋 | 照常演：劇本只用預先帶入的目的地，不需要搜尋；地圖空白不影響操作 |
| **開始或重新開始失敗** | 展示頁按鈕下方出現紅字「開始失敗，請確認後端有在執行。」或「重新開始失敗，請確認後端有在執行。」，「紀錄」旁亮紅點 | 打開「紀錄」看原因。確認後端在跑（`curl http://localhost:8080/api/ping`），再按一次按鈕。還是不行，就在終端機執行 `just backend down && just backend up` 只重啟後端（介面不用動，不要重跑 `just demo`：介面還開著時它會因連接埠被占用而停下） |
| **Demo 中後端停了** | 「紀錄」旁亮紅點，紀錄寫「連不到後端，每秒重試」 | 讓後端恢復（同上）。展示頁每秒重試，後端回來後紀錄寫「後端恢復了」，模擬器與台下操作自己繼續，不必重新開始 |
| **重設後乘客顯示「連線不穩」** | 另外開著、停在請求畫面的乘客分頁一直顯示「連線不穩」 | 重新整理那個分頁。展示頁的重新開始會自動重新載入兩支手機，不受影響 |
| **`driver4` 一直沒變黃** | 乘客一直停在「正在等駕駛確認」 | 打開展示頁右下角的「紀錄」：有沒有「driver5 婉拒了…」；寫著「連不到後端」就先讓後端恢復（見上一列）。按鈕若是「開始 Demo」，代表展示頁被重新整理過、模擬器沒在跑：按「開始 Demo」會重設，從頭來 |
| **送出得太晚** | 紀錄寫「注意：driver5 已經過上車點，之後的請求會直接配給 driver4」 | 照常演：請求會直接配給 `driver4`，跳過婉拒那段，講者略過「第一位駕駛不方便」那句即可 |
| **乘客「目前沒有可搭的車」** | 送出後立即顯示 | 通常是兩位真人駕駛都已經經過上車點，或忘了按「開始 Demo」、忘了讓 `driver4` 出發。按「回去看接近的車」，按「重新開始」兩次後從頭來 |
| **車一直沒到上車點** | 已確認畫面停住 | 展示頁被重新整理或關掉了，模擬器跟著停。只能按「開始 Demo」從頭來（會重設） |
| **要給觀眾看市府戰情室** | — | 按右下角的「市府戰情室」，講完按「手機」換回來。戰情室嵌在展示頁裡，模擬器與台下操作照常執行，兩支手機的畫面也不會重新載入。不要另開戰情室的分頁取代展示頁：離開展示頁車子就停了 |

## 為什麼這樣安排

- **台上的駕駛用強制標籤收請求**：Go 依感受成本排序（REQ-042，design.md 4.11 媒合引擎），最近的模擬車（自動接受）通常最先拿到請求。只有台上的兩位真人駕駛同時帶「不抽菸」和「能放大件行李」，乘客把兩個都設成「一定要」後，請求就一定配給他們（ui-design 8.8）。只用一個標籤不夠：`driver3` 帶「不抽菸」，`driver2` 能放行李，請求會被模擬車搶走。兩個標籤也剛好是兩種方向：「不抽菸」雙方都能選，「能放大件行李」只有駕駛能選（DD-42）。
- **婉拒交給 `driver5`**：只有一位駕駛同時帶這兩個標籤時，婉拒後沒有下一台符合的車，會變成「無車可配」。`driver5` 和 `driver4` 同時出發，但模擬路徑從上車點前約 400 公尺開始（`driver4` 約 535 公尺），一定比 `driver4` 先到上車點，請求會先配給 `driver5`（DD-45）；它婉拒後，改配給台上的 `driver4`，後面的上車、結束共乘、行程結束都在台上那支手機發生。
- **標籤效果演「已放寬」**：同一個請求裡把「安靜坐車」設成「最好」。符合強制條件的兩台車都沒有標「開車喜歡安靜」，平台照樣配給最快的車，並標示「已放寬」，正好說明「建議只加分、不讓乘客多等」的取捨（REQ-047）。不另外安排「標籤勝出」，因為那需要讓幾台車的等待時間接近，現場不好控制。
- **只用一位乘客**：一位乘客有未結束的請求時不能再送出（REQ-069）。取捨、婉拒、確認都在同一個請求裡，就不需要換乘客，也不用先結束共乘再送第二次。
- **台下交給展示頁**（[#191 T62](https://github.com/sohoffice/debugthon-carpool/issues/191)，DD-45、UD-30）：`driver5` 的出發、婉拒與模擬器都由展示頁完成，講者只開一頁，不用切換視窗、不用看終端機，也不需要另一個人。先後順序由路徑距離保證，所以不需要提示講者何時出發，畫面上也沒有只給講者看的提示。`driver5` 沒有上一趟行程（用來展示第一次使用），展示頁直接透過 API 出發，目的地和 `driver4` 相同，模擬器的路徑也開得到。
